# Alpha.34: revision recovery and local runtime proposals

Status: signed test APK delivered; phone acceptance pending. Implementation merged in [PR #69](https://github.com/SEsquieu/atlas/pull/69) and [PR #70](https://github.com/SEsquieu/atlas/pull/70). Tracks [#68](https://github.com/SEsquieu/atlas/issues/68) and advances [#65](https://github.com/SEsquieu/atlas/issues/65).

- Explicit candidate lifecycle and source ancestry, pre-execution stale-base rejection, and preservation of an installed task target during recovery.
- Resumed installed local work can reach native confirmation after discovery; research never authorizes mutations or permissions.
- Local JavaScript runtime inspection, exact source proposals, isolated qualification and native-confirmed selection for new tasks. Current tasks retain their pins. Ordinary tasks see only the status tool until they inspect runtime capabilities.
- Narrow reconciliation of corrected proposal failures and obsolete pre-execution candidate-base failures. Unknown outcomes remain blocking.

One bootstrap APK is necessary to install these native tools and host fixes. Subsequent approved JavaScript guidance/infer-yield changes do not require another APK. Kotlin behavior, schemas, revision/permission rules, context projection and provider transport still do. No repository executor, issue/PR submission service or automatic update feed is installed.

## Phone acceptance

1. Ask Atlas to improve the existing MazeGen app using its judgment. It should stage from current live source, keep the same workspace, test the new candidate and deliver it. A source edit based on candidate bytes must name that parent candidate.
2. If behavior cannot be verified, explicitly request acceptance of the named uncertainty and activation for manual testing. The native confirmation should appear after local work resumes. Reject it once; no approval or activation should be fabricated.
3. In a separate task ask: “Inspect your editable runtime. Propose a small guidance improvement that reduces repeated source reads. Test it, explain its limits, and ask me before selecting it for new tasks.” Approve only the intended proposal. This task must retain its existing runtime pin. A new task should use the selected runtime.
4. Change the default to Native while a task is active. Existing work keeps its pin; fresh tasks use Native. Export the full session and compare core time, provider time, source reads, retries and cumulative tokens separately.

Four isolated contract probes do not prove a general behavioral improvement. Phone acceptance and controlled latency/token benchmarks remain pending.
