# Atlas alpha.20 — task outcomes and rendering evidence

Discarded candidate staging/test/validation failures can be superseded by a later durable activation receipt for the same workspace and base, provided the activated revision is still live. Original calls remain failed in the audit; the task checkpoint records the resolving operation and timestamps. Unknown outcomes and unrelated workspace failures remain blockers. A completed fixture tool with `passed:false` now counts as failure. Ordering is stable when tool proposals share a creation timestamp.

Package activation receipts and pure fixture reports now appear in turn status. Historical slice cards show start/end times and identify themselves as slice history. Normal yields direct the operator to current task status. Task cards distinguish current blockers from superseded candidate errors. Non-error runtime notices no longer use the generic needs-attention heading.

Structural validation and fixture receipts report whether activation was performed and the concrete next step. They no longer say activation is unavailable or confuse a passing fixture check with an authorization grant. Core capability, candidate checks, startup and activation remain distinct facts.

## Rendering correction

The original foreground Compose panel reproduced Neon Vale's white canvas on both Android 15 and 16 despite a loaded stylesheet and correctly computed dark radial gradient. Setting only a dark native fallback changed the canvas to that fallback color and still failed the gradient assertion.

The foreground host now places the Activity-owned WebView inside a native FrameLayout and starts document loading after attachment and layout. The original Neon Vale source paints its authored gradient in the production-panel regression on both Android versions. No app-specific background rewrite or sandbox relaxation was added. Authored opaque backgrounds retain control, including light themes; the native canvas defaults to Atlas dark only while loading or transparent.

Web diagnostics sample actual HTML/body backgrounds, viewport and element geometry, stylesheet availability, resource requests, readiness, Android API and WebView provider/version. The fixed host probe executes no agent-supplied diagnostic code. Its output is bounded and inspection is fenced against surface replacement. Source CSS describes intended appearance, not proof of painted pixels.

Viewport capture now uses PixelCopy on the viewport rectangle in the owning Atlas Activity window instead of a software WebView redraw. The device regression compares captured and displayed pixels. Revision, navigation and session-observation fences remain, and movement/resizing during capture causes an explicit retry error. Cancellation releases the destination bitmap after the asynchronous copy finishes. This does not capture physical camera content or other apps.

Preview fixtures check startup and stylesheet state. Visual acceptance is checked in the actual foreground Compose panel, with a strict gradient assertion that rejects both white pixels and the native dark fallback. A preview handshake or computed CSS never substitutes for foreground pixel evidence.

## Diagnostic exports and checkpoints

Session ZIPs include an index and up to eight available workspace viewport images within an 8 MiB image budget, newest first. Missing/limited images are explicitly marked; up to 64 capture metadata entries are indexed. Physical camera images are excluded. Main-process exit history is separated from worker cleanup history; Android's retained history remains limited.

Oversized whole turns containing large tool payloads can be checkpointed using bounded previews, original-message IDs and hashes. Dialogue remains intact and full source/audit payloads remain durable. Checkpoints advance only through complete represented turns. An oversized dialogue still fails safely rather than silently skipping history.
